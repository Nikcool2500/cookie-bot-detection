# Детекция ботов по поведению cookie

Тестовое задание Авито (команда Антибота) для отбора на буткемп.

Есть сервисы, которые автоматически собирают данные с объявлений: цены, сводки по категориям, контакты продавцов. Нужно по событиям cookie за сутки отличить такой трафик от человеческого и выдать каждой cookie score от 0 до 1.

Итог на своей временной валидации: **P@R≥0.7 = 0.745** против 0.09 у простого baseline.

## Данные

Данные выдавались под задание, в репозиторий они не входят.

- `train.csv` / `test.csv` — одна строка на cookie: время создания, границы суточного окна наблюдения, в train ещё `target`. Около 11 тыс. cookie в train, ботов примерно 8%.
- `events.csv.gz` — лог событий: тип события, платформа, User-Agent, объявление (id, категория, локация, тип продавца), поисковый запрос и страница выдачи, координаты курсора.

Готовых признаков нет, всё собирается из событий. Условие задачи: признаки должны быть доступны на момент конца окна.

## Метрика

Precision при Recall ≥ 0.7: среди порогов, при которых находим не меньше 70% ботов, берётся максимальный precision. Cookie с одинаковым score считаются одной группой. Реализация организаторов лежит в `metric.py`, ей же считается вся локальная валидация.

## Решение

### Подготовка событий

- Беру только события внутри окна своей cookie: `window_start_ts <= event_ts < window_end_ts`.
- Удаляю полные дубли строк. На метрику это не повлияло, оставил для порядка.
- `platform` встречается в 11 написаниях (`WEB`, `Web`, `desktop`, `iphone`, `IOS`...), свожу их к `web / android / ios`.

### Признаки

Около сотни признаков, по группам:

- **Тайминги.** Самая полезная группа. Интервалы между событиями: медиана, квантили, коэффициент вариации, доля интервалов меньше секунды, максимум событий за 10 с и за минуту, автокорреляция интервалов, энтропия по часам. Бот отличается ритмом, а не количеством действий.
- **Разнообразие.** Число уникальных объявлений, категорий, локаций, запросов, максимальная страница выдачи, просмотров на одно объявление.
- **Состав событий.** Счётчики и доли 10 типов событий, отношения контактов и избранного к просмотрам, капча, логин.
- **Курсор.** Доля событий с координатами, доля точек `(0, 0)`, разброс, длина прыжков между точками, доля движений строго по одной оси.
- **User-Agent.** Флаг библиотечных клиентов (`python-requests`, `okhttp`, headless и т.п.), браузер, мажорная версия, ОС, несовпадение `platform` и UA. Сырую строку UA как категорию не беру, уникальных значений слишком много.
- **Возраст cookie** на начало и конец окна.
- **Синхронность с другими cookie.** Сколько чужих событий было рядом по времени. Идея в том, что боты одного сервиса ходят пачками.
- **Композиты** вроде «интенсивность × регулярность».

Пропуски: счётчики и доли заполняю нулём, величины, которые без событий не определены (интервалы, разброс курсора), заполняю `-1`, категории — `"unknown"`. Категории в test приводятся к тем же уровням, что в train, иначе коды в LightGBM/XGBoost разъезжаются.

### Как избегал утечки из будущего

Больше всего внимания ушло на признаки синхронности, их легко посчитать с утечкой.

- Пул событий общий для train и test, без `target`. Если считать отдельно, у test счётчики систематически другие.
- Для события в момент `t` учитываются только чужие события из `(t − W, t]`.
- Абсолютные счётчики нормирую на плотность пула, она меняется во времени.
- Есть проверка `check_point_in_time`: выбрасываю все события после момента `T` и проверяю, что признаки cookie с `window_end <= T` не изменились.

Признаки, которые зависели от состава выборки (размер когорты cookie), в итоге удалил.

### Валидация

Test лежит позже train по времени, поэтому валидация тоже по времени:

- holdout — последние 20% train по `window_start_ts`;
- в обучение попадают только cookie, у которых окно закончилось до начала holdout, чтобы окна не пересекались;
- для оценки стабильности и подбора параметров — 3 временных фолда (expanding window) с тем же зазором.

### Модель

LightGBM и XGBoost, взвешенное среднее вероятностей. Дисбаланс классов учитывается через `sample_weight` (balanced). Гиперпараметры подобраны Optuna (TPE, 130 trials на модель) по средней P@R≥0.7 на трёх фолдах. Вес ансамбля выбран сеткой на holdout. Финальные модели переобучаются на всём train.

## Результаты

На holdout (seed 42):

| Модель | P@R≥0.7 | ROC-AUC | PR-AUC |
|---|---|---|---|
| Константа (доля ботов) | 0.082 | | |
| RandomForest на 2 признаках (`n_events`, `item_nunique`) | 0.092 | | |
| LightGBM + Optuna | 0.733 | 0.927 | 0.750 |
| XGBoost + Optuna | 0.726 | 0.931 | 0.758 |
| Ансамбль (0.6 LGBM + 0.4 XGB) | **0.745** | | |

На трёх временных фолдах LightGBM даёт 0.68–0.70 при std около 0.01. Эта оценка честнее, чем один holdout.

### Абляция

Убирал группы признаков по одной (LightGBM, одинаковые параметры):

| Без чего | P@R≥0.7 |
|---|---|
| Все признаки | 0.713 |
| без таймингов | 0.651 |
| без композитов | 0.670 |
| без возраста cookie | 0.688 |
| без синхронности | 0.697 |
| без UA-флагов | 0.713 |

Флаги UA вклада не дали: этот сигнал уже покрыт другими признаками. Синхронность по одному и тому же объявлению тоже ничего не добавила, в выборке слишком мало пересечений. Пробовал ещё «редкость UA за последние 24 часа», прироста не было, признак убрал.

## Ограничения

- Положительных в holdout около 230, поэтому метрика шумит на ±0.02–0.03.
- Вес ансамбля выбран на том же holdout, на котором и оценивается, так что 0.745 немного оптимистично.
- Боты в разметке — только известные сервисы. Как модель поведёт себя на ботах, которые хорошо имитируют человека, по этим данным не проверить.
- Признаки синхронности зависят от плотности выборки. В реальном потоке соседей будет гораздо больше, нормировка на фон частично это компенсирует, но признак остаётся самым хрупким.

## Запуск

Python 3.13.

```bash
pip install -r requirements.txt
```

Положить `train.csv`, `test.csv`, `events.csv.gz` в `data/` и выполнить `solution_final.ipynb` целиком. На выходе получится `submission.csv` с колонками `cookie_id, score`.

Подбор гиперпараметров по умолчанию выключен (`RUN_OPTUNA = False`), найденные параметры сохранены в коде. Если включить, поиск займёт около 25 минут.

## Файлы

- `solution_final.ipynb` — решение целиком: признаки, валидация, модели, сабмит.
- `metric.py` — официальная метрика от организаторов.
- `requirements.txt` — зависимости.

Использованы pandas, NumPy, scikit-learn, LightGBM, XGBoost, Optuna.
